# OWC LTO-8 Archiver v1.0.0-rc.1 (pre-release)

OWC LTO-8 Archiver is a Windows command-line tool that archives data to
LTO/LTFS tape: it fetches files from a local folder or a remote host over SSH,
packs small files into bundles, writes them to an LTFS-mounted cartridge with
`robocopy`, and records every file in a searchable catalog so it can be found
and restored later.

> **This is a release candidate, not a stable release.** No working tape
> drive was available while it was prepared, so **nothing in this release has
> been validated on a real drive and cartridge**. Read
> [Known limitations](#known-limitations) before using it on data you care
> about.

Program version: `1.0.0rc1` (`python run.py --version`). Python 3.11 – 3.14.
Windows only.

## Highlights

### A second catalog backend: SQLite

The catalog can now live in a single local SQLite file instead of a
PostgreSQL server. Choose it in `config.ini`:

```ini
[DATABASE]
backend = sqlite
sqlite_path = lto_archive.sqlite3
```

- The file and its complete schema are created automatically on first run.
  There is no server to install and no database driver to install.
- It is the same code base and the same package: the backend is one line of
  configuration, not a separate build.
- The schema guards that protect the PostgreSQL catalog (write-once container
  identity, the chunk-transition guard, sealed artifacts, …) are enforced on
  SQLite by triggers of the same names.
- A single-writer archiver lock that cannot be left stuck: it is an
  operating-system file lock, released by the OS when the process exits,
  crashes or is killed.
- Online catalog backup with an integrity and foreign-key check
  (`python run.py --backup-db`, or menu option 9).
- The catalog test suites run on SQLite with no server, and on PostgreSQL
  when a disposable test server is configured.

Details: `docs/database-backends.md` in the package.

### Audit fixes

This release contains the fixes from a full code audit. By theme:

**Tape-write safety**

- The tape-writing `robocopy` is isolated from a console Ctrl+C, and
  `scripts/graceful_stop.py` refuses to signal a run while a tape write is
  active.
- A chunk is marked `backing` before the first touch of the tape, and its
  staged pack is kept on every writer error.
- The local (attended) archive path no longer ejects the cartridge after each
  chunk, and now runs the same pre-write safety gates as the remote pipeline
  (LTFS sync mode, media health, pending restart), failing closed when a gate
  cannot be evaluated. It refuses to write when the cartridge label cannot be
  read.
- The archiver lock is proven to be still held before every tape write.
- Chunk state transitions are enforced in the setter and in the database:
  a chunk in `backing` may only move to `done`, and `done` is final.
- The local writer refuses a tape marked full, or over its budget, also for a
  chunk that was already assigned to it.
- Eject and repair in the tape-maintenance menu require a typed confirmation.
- The pending-restart (SCCM) check fails closed without blocking hosts that
  have no SCCM client.
- Drive and medium health are re-checked from the passive IBM log before each
  chunk of a write group.
- The `robocopy` result classifier rejects a failed directory and unaccounted
  bytes.

**Data integrity on the way to tape**

- Planned, fetched and packed files are reconciled before a chunk may reach
  the writer.
- Remote files are requested by their exact name (never whitespace-stripped).
- Extracted names are matched across Unicode normalisation forms, and a file
  is recorded as missing at the source only when the source host positively
  reports it missing.
- Chunks are filled across directories instead of one chunk per directory.
- Stored TAR carries sparse files with trailing holes and hard-linked names,
  and loose large files are carried through a mixed Stored TAR chunk.
- The fetch watchdog no longer cancels healthy fetches; the remote scan is
  bounded.
- Per-file manifests are protected from overwrite, lost writes and trailing
  data.

**Truthful and safe restore**

- Restore reports what was really restored and returns a failure status when
  it was incomplete; a directory-catalog error during a directory restore is a
  failed restore.
- Every restore destination is contained inside the restore directory.
- Legacy ZIP members are extracted atomically and a bad member no longer
  stops the rest; restore never picks one of several same-named ZIP members.
- Catalog-backup verification reads the whole dump and states what it did not
  prove; the campaign-store verifier fails when it verified nothing.

**Inspector GUI stability**

- Background workers are kept alive until their reply is delivered.
- Deleting an active session is refused; destructive actions need a typed
  confirmation; paging is safe; a database that is down gives a readable
  error.
- One tape-usage percentage is shown, measured against the planning budget.

**Strict configuration**

- `config.ini` is validated at start-up. A bad value stops the run with a
  message naming the section, key and value instead of being guessed at.
  `config.example.ini` is kept in step with the code.

**Stronger tests**

- Tests prove that both tape writers obey their pre-write gates.
- An opt-in mutation check for the safety gates.
- Source-substring assertions were replaced by behaviour or AST facts.
- The PostgreSQL test guard is fail-closed: it refuses port 5432, a
  non-loopback host, any connection parameter that could redirect the
  connection, and a server that hosts a production catalog.
- Tests no longer read the untracked `config.ini` in the project folder.

## Installation

There is **one package**. Pick the dependency set that matches the backend
you want; you can switch later by installing the other set and changing
`config.ini` (note: there is no tool that copies catalog data between the two
backends).

Unzip `owc-lto8-archiver-1.0.0rc1.zip`, open PowerShell in the unzipped
folder, and create a virtual environment:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

### Option 1 — SQLite (recommended for a new setup)

```powershell
python -m pip install -r requirements-core.txt
Copy-Item config.example.ini config.ini
# edit config.ini: paths, [HARDWARE] lto_drive and ltfs_ownership_id, [REMOTE]
python run.py --version
python run.py
```

`config.example.ini` already says `backend = sqlite`. The catalog file is
created on the first run. It must be on a local disk, not a network share.

### Option 2 — PostgreSQL

```powershell
python -m pip install -r requirements-postgres.txt
Copy-Item config.example.ini config.ini
# edit config.ini: set [DATABASE] backend = postgresql and host / port /
# dbname / user, then the paths, [HARDWARE] and [REMOTE] sections
Copy-Item .env.example .env
# edit .env: set PGPASSWORD
docker compose up -d db
python run.py --version
python run.py
```

On a **new, empty** PostgreSQL database the first run installs the complete
schema and prints one line saying so; the database is ready to archive. This
happens only when the database held no table at all before that start. An
**existing** catalog is never migrated implicitly: there the directory-catalog
and later schema migrations stay explicit steps
(`python inspect_db.py --apply-*-schema`, each of which asks for a verified
`pg_dump` backup).

### Optional — the DB Inspector GUI

```powershell
python -m pip install -r requirements-gui.txt
python inspect_db.py
```

`requirements.txt` still installs everything (core + PostgreSQL + GUI), as it
always did.

## Upgrade notes for existing PostgreSQL installations

- **Your backend does not change.** A `config.ini` with no `backend` line
  keeps using PostgreSQL. Only new configurations select SQLite.
- **One new schema migration is applied automatically at start-up:**
  `scripts/sql/020_postgres_chunk_transition_guard.sql`. It is additive (one
  small table, one index, one function, one row trigger), rewrites no data and
  is idempotent. After it, the database itself refuses to move a chunk out of
  `backing` (except to `done`) or out of `done`.
- **Strict configuration parsing may reject a `config.ini` that used to
  load.** The error message names the section, key and value. To fix:
  - *Inline comments are not allowed.* `guard = true ; keep on` is an error.
    Move the comment to its own line above the setting.
  - Yes/no settings accept only `true false yes no on off 1 0`.
  - Numbers must be finite and inside the documented range.
  - A key the program does not know (usually a typo) is reported as a
    warning and otherwise ignored — check the warnings on the first start.
  - Compare your file with the new `config.example.ini`.
- **Restore changes the names it writes when they are unsafe on Windows.**
  Colons, characters NTFS does not allow, trailing dots and spaces, and DOS
  device names (`CON`, `NUL`, …) are neutralised, and a destination that
  would land outside the restore directory is refused. A restored file can
  therefore have a slightly different name from the one in the catalog.
- **The local archive path no longer ejects the cartridge after each chunk.**
  It ejects only at the end of a completed session, only when
  `[HARDWARE] eject_after_session = true`, and only after `EJECT` is typed.
  The remote pipeline never ejects.
- **Exit codes are now non-zero on failure.** `run.py` used to print some
  errors and still exit 0 (a failed `--backup-db`, a headless run that could
  not reach the database, a failed menu action, an incomplete restore).
  Scheduled tasks and scripts that ignored the exit code will now see
  failures. The codes are defined in `src/exit_codes.py`.
- **The watchdog refuses to auto-restart after more stop reasons.**
  `scripts/archive_watchdog.ps1` now decides on the stop reason *and* the exit
  code, covers reasons that need a human (an unverifiable LTFS mount,
  ambiguous active sessions, configuration errors, an operator stop, a lost
  archiver lock), and fails closed on an unknown or missing code.
- Install or refresh dependencies with
  `python -m pip install -r requirements-postgres.txt` (or keep using
  `requirements.txt`). The version floors are unchanged.

## Known limitations

- **Not validated on a real tape drive and cartridge.** In this release all
  tape-path behaviour — writing, LTFS readiness, cartridge verification,
  eject, restore from tape — is verified only with simulated devices and
  temporary directories standing in for the tape. Treat the first runs on real
  hardware as a pilot: start with a small, non-critical data set.
- **PostgreSQL-only features.** These refuse on SQLite with one readable line
  and change nothing (the list is `POSTGRESQL_ONLY_FEATURES` in
  `src/db_backend.py`):
  - explicit schema migration commands (`inspect_db.py --apply-*-schema`,
    `--create-migrated-db`, `--apply-directory-catalog-schema`);
  - legacy data backfill / transition / rehearsal commands (directory-catalog
    backfill, legacy-session transition, frontier bootstrap, membership backfill,
    plan-1 rehearsal);
  - another database on the same PostgreSQL server
    (`inspect_db.py --db`, `--compare-db` / `--with-db`);
  - the schema provenance audit;
  - sealed tape-write batches and their observation mode;
  - small-file manifest export / validate / prune (the file-based manifest
    search used by restore still works);
  - Stored-TAR packaging boundaries — so **SQLite sessions always use ZIP
    packaging**;
  - `pg_dump` based backup, restore-verification and migrated-database
    creation (on SQLite use `python run.py --backup-db`).
- **A tape reset takes two commands and has not been run on hardware.** The
  menu refuses to format a labelled cartridge and points to `run.py
  tape-reset`. Its impact report is written by the read-only
  `python run.py tape-reset --tape <LABEL> --prepare-impact-report <FILE> --backup-file <BACKUP>`
  (PostgreSQL also needs `--scratch-host`, `--scratch-port` and
  `--scratch-user` to prove the dump restores). See the
  [user guide](../user-guide.md#tape-maintenance-option-3).
- **Stored-TAR chunks cannot be rewritten after a tape reset.** A destructive
  tape reset returns the cartridge's chunks to `pending`, but a Stored-TAR
  chunk still owns its recorded containers and re-writing it fails closed at
  staging. ZIP chunks can be re-written as before.
- **Windows only.** The program depends on `robocopy`, the IBM LTFS tools and
  Windows drive semantics.
- **The POSIX code path of the SQLite archiver lock is untested.** It exists,
  but every test run so far has been on Windows.
- **No SQLite ↔ PostgreSQL data migration tool.** A catalog cannot be moved
  from one backend to the other in this release.
- **Name search on SQLite is case-insensitive for ASCII letters only**
  (`LIKE` / `ILIKE`). Non-ASCII letters match case-sensitively. There are no
  trigram indexes on SQLite, so substring search scans the table.
- **An existing PostgreSQL catalog that predates the explicit migrations
  still needs them applied by hand** before a packed archive run; only a
  database that was completely empty is completed automatically (see
  Installation, Option 2).
- A catalog backup is refused when its destination is on the drive letter
  configured as `[HARDWARE] lto_drive`. Keep the project folder (or the
  backup folder) on a different drive from the tape. With `lto_drive` left
  blank (no tape drive configured) the refusal does not apply.
